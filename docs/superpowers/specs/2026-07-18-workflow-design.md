# 설정 시스템 설계: 지라 구조 모방 — 전역 관리 + 스킴 배정 + 프로젝트 커스텀 (2026-07-18, v3)

설정 시스템 합의 순서 C(워크로그, 완료)→B(이슈 타입)→A(워크플로 상태). 영향 범위가 가장
넓어 설계를 먼저 굳혀 둔다. **v3 개정: 지라의 실제 설정 구조를 모방한다** — 전역 관리(⚙)에서
설정 세트(스킴)를 정의하고 프로젝트에 배정(공유)하며, 프로젝트는 독립 커스텀으로도 전환
가능(지라 회사관리형=스킴 공유 / 팀관리형=독립의 이중 구조 그대로).

## 구조 (지라 모방)

```
전역 관리 (⚙ /settings)
├─ 워크플로 스킴들   ── "기본 워크플로"(디폴트) + 사용자가 추가한 세트들
├─ 이슈 타입 스킴들  ── "기본 타입 세트"(디폴트) + …
   ↓ 배정(assign) — 여러 프로젝트가 같은 스킴을 공유
프로젝트 설정
├─ 스킴 사용(기본): 배정된 스킴을 따른다. 스킴 수정 → 공유 중인 모든 프로젝트 즉시 반영
└─ 프로젝트 커스텀(팀관리형식): 현재 스킴 값을 복사해 독립 — 이후 스킴 변경 무영향
```

- 새 프로젝트는 **디폴트 스킴**을 배정받는다 (지라의 Default Scheme).
- 스킴 삭제는 배정된 프로젝트가 없을 때만 (지라와 동일). 디폴트 스킴은 삭제 불가.
- 커스텀 → 스킴 복귀: 커스텀 폐기, 사라지는 상태의 이슈는 이관 확인(아래).

## 데이터 모델

```ts
interface WorkflowStatus {
  id: string;            // 불변 (이슈가 참조)
  name: string;          // "코드 리뷰" 등 — 세트 내 유일
  category: IssueStatus; // "todo" | "inprogress" | "done" — 기존 타입을 카테고리로 재사용
  order: number;
}

/** 설정 본문 — 스킴과 프로젝트 커스텀이 같은 형태를 공유한다 */
interface SettingsBody {
  statuses: WorkflowStatus[];   // A: 워크플로 (기본: 할 일/진행 중/완료)
  enabledTypes: IssueType[];    // B: 사용할 이슈 타입 (기본 전체, subtask 항상 포함)
  // 이후 설정(워크로그 정책 등)도 여기에 필드로 추가 — 자동으로 같은 구조를 얻는다
}

interface SettingsScheme {
  id: string;
  name: string;          // "기본 워크플로" 등
  isDefault: boolean;    // 새 프로젝트에 자동 배정, 삭제 불가
  body: SettingsBody;
}

// JiraData에 추가:
//   schemes: SettingsScheme[]                            — 전역 관리가 정의
//   projectSettings: {
//     projectId: string;
//     schemeId: string;             — 배정된 스킴 (커스텀 중에도 복귀 대상으로 유지)
//     custom: SettingsBody | null;  — null = 스킴 사용, 값 = 프로젝트 독립 커스텀
//   }[]
```

**해석 함수(스토어의 단일 진실)**:
`resolveSettings(projectId): { body: SettingsBody; source: "scheme" | "custom"; scheme: SettingsScheme }`
— 모든 화면·검증은 이 함수만 통해 설정을 읽는다.

**마이그레이션(normalize)**: schemes 없으면 디폴트 스킴 1개(기본 3상태 — id를 기존
"todo"/"inprogress"/"done"과 동일하게 + 전 타입)를 생성하고, 모든 프로젝트를
`{ schemeId: 디폴트, custom: null }`로 배정. → **기존 Issue.status 값·저장 데이터 100% 호환.**

## 핵심 전략: 카테고리 불변, 상태만 가변 (v1 유지)

모든 상태는 카테고리 3종 중 하나에 필수 소속 → 대시보드/타임라인 색/완료 판정/스프린트
완료 복귀/차단됨 경고 등 기존 로직은 카테고리 기준으로 무수정 동작.

## 규칙 (스토어 검증)

- 상태: 이름·카테고리 필수, 카테고리별 최소 1개, id 불변(이름 변경 자유)
- 상태 삭제(스킴/커스텀 공히): 해당 상태를 쓰는 이슈를 같은 카테고리의 첫 상태로 이관.
  **확인 모달에 "어느 프로젝트에서 몇 건이 어디로" 명시** (스킴 삭제는 공유 프로젝트 전체 집계)
- 스킴: 배정된 프로젝트가 있으면 삭제 불가, 디폴트 스킴은 삭제 불가·디폴트 이전 후 교체
- 프로젝트 스킴 재배정: 새 스킴에 없는 상태의 이슈 이관 확인 후 schemeId 교체
- 타입 비활성화: 그 타입의 기존 이슈는 유지(표시만), 새로 만들 때 선택지에서 제외.
  subtask는 항상 활성(계층 기능 의존)
- 커스텀 → 스킴 복귀: 스킴에 없는 상태의 이슈 이관 확인 후 custom=null

## UI (지라 관리 화면 모방)

- **전역 관리 페이지 `/settings`** (신규) — 상단바 ⚙ 진입. 좌측 메뉴(지라 관리자 화면식):
  워크플로 스킴 / 이슈 타입 스킴. 스킴 목록(이름·디폴트 배지·배정 프로젝트 N개) →
  스킴 편집(상태/타입 편집기) · 새 스킴 · 삭제(배정 없을 때만).
- **프로젝트 설정 페이지** — 탭 재구성: 일반 / 워크플로 / 이슈 타입. 각 탭 상단에
  **"스킴: {이름} 사용 중" 배지 + 스킴 변경 Select + "이 프로젝트만 커스텀" 스위치**.
  스킴 사용 중엔 읽기 전용 미리보기("전역 관리에서 편집" 링크), 커스텀이면 편집 가능 +
  "스킴으로 복귀".
- 상태 편집기(공용): 목록(이름 · 카테고리 Lozenge · 순서 ↑↓ · 삭제), 추가 폼.

## 영향 지도 (구현 시 수정 지점)

| 영역 | 변경 |
|---|---|
| `labels.ts` | `statusLabel/appearance` 함수화 — resolveSettings 기반, appearance는 카테고리로 |
| 보드 | `BOARD_STATUSES` 상수 → resolveSettings(projectId).statuses(order순). Board.columns는 statusId 참조 |
| 이슈 목록/상세/만들기 Select | 프로젝트 해석 결과 사용 (타입 Select는 enabledTypes) |
| 스마트 검색 `상태:` | 카테고리 라벨 + 상태 이름 둘 다 매칭 |
| 대시보드/타임라인/홈 | 카테고리 기준 — 무수정 또는 경미 |
| 전역 만들기 모달 | 선택한 프로젝트의 enabledTypes 반영 |

## 구현 순서 (착수 시)

1. 모델+normalize+resolveSettings+스킴/커스텀 CRUD(이관 로직) — 기존 테스트 전부 통과가 1차 관문
2. B 먼저 노출: 전역/프로젝트 설정의 "이슈 타입" 탭 + 생성 UI 반영 (작고 독립적)
3. A: labels 함수화 + 보드/목록/상세/검색 치환 + 워크플로 탭
4. 스마트 검색 상태 이름 확장

## 범위 제외

상태 전이 규칙(다이어그램), 상태별 권한, 보드별 컬럼 숨김, 크로스 프로젝트 이동,
설정 변경 이력(감사 로그 — 백엔드 BACKLOG).
