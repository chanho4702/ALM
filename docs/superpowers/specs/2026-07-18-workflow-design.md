# 커스텀 워크플로(상태) 설계 (2026-07-18) — 설계 선행, 구현은 설정 시스템 A 차례

설정 시스템 합의 순서 C(워크로그, 완료)→B(타입 지정)→**A(이 문서)**. 영향 범위가 가장 넓어
설계를 먼저 굳혀 둔다. 프로젝트별 이슈 타입 지정(B)도 이 문서의 설정 모델에 얹는다.

## 핵심 전략: 카테고리 불변, 상태만 가변

지라와 동일한 접근 — 상태는 프로젝트마다 자유지만, 모든 상태는 **카테고리 3종
(`todo` | `inprogress` | `done`)** 중 하나에 반드시 속한다. 이 덕분에:

- 대시보드/타임라인 색/보드 "완료" 판정/스프린트 완료 시 백로그 복귀/차단됨 경고 등
  기존 로직은 전부 **카테고리 기준으로 그대로 동작** (수정 최소화)
- 스마트 검색 `상태:진행중`은 카테고리 검색으로, `상태:"코드 리뷰"`는 상태 이름 검색으로 확장

## 데이터 모델

```ts
interface WorkflowStatus {
  id: string;            // 불변 (이슈가 참조)
  name: string;          // "코드 리뷰" 등 — 프로젝트 내 유일
  category: IssueStatus; // "todo" | "inprogress" | "done" — 기존 타입을 카테고리로 재사용
  order: number;         // 보드 컬럼/드롭다운 순서
}

interface ProjectSettings {
  projectId: string;
  statuses: WorkflowStatus[];     // 기본: 할 일/진행 중/완료 3개 (id는 카테고리와 동명)
  enabledTypes: IssueType[];      // B: 프로젝트에서 쓸 타입 (기본 전체) — subtask는 항상 포함
}
// JiraData.projectSettings: ProjectSettings[]
// Issue.status: string (WorkflowStatus.id 참조로 의미 변경 — 마이그레이션 아래)
```

**마이그레이션(normalize)**: projectSettings 없는 프로젝트에 기본 3상태 생성 —
`id`를 기존 값("todo"/"inprogress"/"done")과 동일하게 두면 **기존 Issue.status가 무수정으로
유효**하다. 저장 데이터 호환 100%.

## 규칙 (스토어가 단일 진실)

- 상태 추가: 이름·카테고리 필수. 카테고리별 최소 1개 유지(카테고리가 비는 삭제 금지)
- 상태 삭제: 그 상태의 이슈들을 같은 카테고리의 첫 상태로 이관 후 삭제 (확인 모달에 이관 대상 표시)
- 상태 이름 변경: id 불변이라 이슈 무영향
- `moveIssue`/보드 order 재계산의 "컬럼" 단위가 status id로 그대로 유지됨 (로직 무수정)
- 이슈를 다른 프로젝트로? — 미지원(현행과 동일)이므로 상태 불일치 문제 없음

## 영향 지도 (구현 시 수정 지점)

| 영역 | 변경 |
|---|---|
| `labels.ts` STATUS_LABELS/APPEARANCE | 함수화: `statusLabel(project, statusId)` / appearance는 **카테고리**로 결정 |
| 보드 컬럼 | `BOARD_STATUSES` 상수 → 프로젝트 상태 목록(order순). Board.columns는 statusId 참조로 변경, 컬럼 추가/삭제가 상태 추가/삭제와 동치가 됨 (보드별 컬럼 숨김은 후속) |
| 스윔레인/WIP/퀵필터 | statusId 기준으로 그대로 |
| 이슈 목록/상세 Select | 프로젝트 상태 목록 사용 |
| 대시보드/타임라인/홈 | 카테고리 기준 — 무수정 또는 경미 |
| 스마트 검색 | `상태:` 값을 카테고리 라벨 + 프로젝트 상태 이름 둘 다 매칭 |
| 통계(진행률 등) | category === "done" 판정으로 통일 |

## 설정 UI (D의 그릇)

`ProjectSettingsPage`를 탭으로 재구성: **일반**(현행) / **워크플로**(상태 목록 — 이름·카테고리
Lozenge·순서 ↑↓·추가/삭제(이관 확인)) / **이슈 타입**(B: 타입 on/off 체크, 최소 1개 + subtask 고정).

## ALM 특색

- 지라의 워크플로 다이어그램(전이 규칙) 대신 **"모든 상태 간 이동 자유 + 카테고리만 강제"** —
  작은 팀에 필요한 유연함은 유지하면서 학습 비용 제거. 전이 제한은 백엔드 권한과 함께 후속.
- 상태 삭제 시 이슈 자동 이관을 확인 모달에 **몇 건이 어디로 가는지** 명시 (정직한 미리보기 원칙).

## 구현 순서 제안 (착수 시)

1. 모델+normalize+스토어(설정 CRUD·이관 로직) — 기존 테스트 전부 그대로 통과가 1차 관문
2. labels 함수화 + 소비처 치환 (보드/목록/상세/검색)
3. 설정 페이지 탭 UI (워크플로 + 이슈 타입 B 동시)
4. 스마트 검색 상태 이름 확장

## 범위 제외

상태 전이 규칙(다이어그램), 상태별 권한, 보드별 컬럼-상태 매핑 커스텀(숨김), 크로스 프로젝트 이동.
