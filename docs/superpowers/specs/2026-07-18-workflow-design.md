# 설정 시스템 설계: 공통 + 프로젝트별 커스텀 2계층 (2026-07-18, v2)

설정 시스템 합의 순서 C(워크로그, 완료)→B(이슈 타입)→A(워크플로 상태). 영향 범위가 가장
넓어 설계를 먼저 굳혀 둔다. **v2 개정: 모든 설정은 "공통(워크스페이스) 기본" +
"프로젝트별 커스텀(오버라이드)" 2계층**이어야 한다는 요구 반영.

## 2계층 원칙 (모든 설정 공통)

```
워크스페이스 공통 설정 (기본값)
   ↓ 상속 (기본)
프로젝트 ── 커스텀 전환 시 공통 값을 복사해서 시작 → 이후 독립
```

- **상속이 기본**: 새 프로젝트는 공통 설정을 따른다. 공통 설정을 바꾸면 상속 중인 모든
  프로젝트에 즉시 반영된다.
- **커스텀 전환**: "이 프로젝트만 다르게" 스위치를 켜면 그 시점의 공통 값을 복사해 독립.
  이후 공통 변경의 영향을 받지 않는다.
- **공통으로 되돌리기**: 커스텀 폐기. 되돌리며 사라지는 상태의 이슈는 이관 확인(아래).
- 지라 대비: 회사관리형(스킴 공유)과 팀관리형(독립)의 장점만 — 스킴이라는 별도 개념 없이
  상속/전환 스위치 하나로 해결하는 것이 ALM 특색.

## 데이터 모델

```ts
interface WorkflowStatus {
  id: string;            // 불변 (이슈가 참조)
  name: string;          // "코드 리뷰" 등 — 세트 내 유일
  category: IssueStatus; // "todo" | "inprogress" | "done" — 기존 타입을 카테고리로 재사용
  order: number;
}

/** 설정 본문 — 공통과 프로젝트 커스텀이 같은 형태를 공유한다 */
interface SettingsBody {
  statuses: WorkflowStatus[];   // A: 워크플로 (기본: 할 일/진행 중/완료)
  enabledTypes: IssueType[];    // B: 사용할 이슈 타입 (기본 전체, subtask 항상 포함)
  // 이후 설정(워크로그 정책 등)도 여기에 필드로 추가 — 자동으로 2계층을 얻는다
}

// JiraData에 추가:
//   workspaceSettings: SettingsBody                     — 공통(전역) 기본
//   projectSettings: { projectId; custom: SettingsBody | null }[]
//                                                        — null = 공통 상속
```

**해석 함수(스토어의 단일 진실)**:
`resolveSettings(projectId): { body: SettingsBody; source: "workspace" | "custom" }`
— 모든 화면·검증은 이 함수만 통해 설정을 읽는다.

**마이그레이션(normalize)**: workspaceSettings 없으면 기본 3상태(id를 기존
"todo"/"inprogress"/"done"과 동일하게)+전 타입으로 생성, projectSettings는 전부
`custom: null`(상속). → **기존 Issue.status 값·저장 데이터 100% 호환.**

## 핵심 전략: 카테고리 불변, 상태만 가변 (v1 유지)

모든 상태는 카테고리 3종 중 하나에 필수 소속 → 대시보드/타임라인 색/완료 판정/스프린트
완료 복귀/차단됨 경고 등 기존 로직은 카테고리 기준으로 무수정 동작.

## 규칙 (스토어 검증)

- 상태: 이름·카테고리 필수, 카테고리별 최소 1개, id 불변(이름 변경 자유)
- 상태 삭제(공통/커스텀 공히): 해당 상태를 쓰는 이슈를 같은 카테고리의 첫 상태로 이관.
  **확인 모달에 "어느 프로젝트에서 몇 건이 어디로" 명시** (공통 삭제는 상속 프로젝트 전체 집계)
- 타입 비활성화: 그 타입의 기존 이슈는 유지(표시만), 새로 만들 때 선택지에서 제외.
  subtask는 항상 활성(계층 기능 의존)
- 커스텀 → 공통 되돌리기: 공통에 없는 상태의 이슈 이관 확인 후 custom=null

## UI

- **전역 설정 페이지 `/settings`** (신규) — 상단바 ⚙ 진입. 탭: 워크플로 / 이슈 타입.
  "이 설정을 상속 중인 프로젝트 N개" 안내.
- **프로젝트 설정 페이지** — 탭 재구성: 일반 / 워크플로 / 이슈 타입. 워크플로·타입 탭 상단에
  **"공통 설정 사용 중" 배지 + "이 프로젝트만 커스텀" 스위치**. 상속 중엔 읽기 전용 미리보기
  ("공통 설정에서 편집" 링크), 커스텀이면 편집 가능 + "공통으로 되돌리기".
- 상태 편집기: 목록(이름 · 카테고리 Lozenge · 순서 ↑↓ · 삭제), 추가 폼.

## 영향 지도 (구현 시 수정 지점)

| 영역 | 변경 |
|---|---|
| `labels.ts` | `statusLabel/appearance` 함수화 — resolveSettings 기반, appearance는 카테고리로 |
| 보드 | `BOARD_STATUSES` 상수 → resolveSettings(projectId).statuses(order순). Board.columns는 statusId 참조 |
| 이슈 목록/상세/만들기 Select | 프로젝트 해석 결과 사용 (타입 Select는 enabledTypes) |
| 스마트 검색 `상태:` | 카테고리 라벨 + 상태 이름 둘 다 매칭 |
| 대시보드/타임라인/홈 | 카테고리 기준 — 무수정 또는 경미 |
| 전역 만들기 모달 | 선택한 프로젝트의 enabledTypes 반영 |

## 구현 순서 (착수 시)

1. 모델+normalize+resolveSettings+공통/커스텀 CRUD(이관 로직) — 기존 테스트 전부 통과가 1차 관문
2. B 먼저 노출: 전역/프로젝트 설정의 "이슈 타입" 탭 + 생성 UI 반영 (작고 독립적)
3. A: labels 함수화 + 보드/목록/상세/검색 치환 + 워크플로 탭
4. 스마트 검색 상태 이름 확장

## 범위 제외

상태 전이 규칙(다이어그램), 상태별 권한, 보드별 컬럼 숨김, 크로스 프로젝트 이동,
설정 변경 이력(감사 로그 — 백엔드 BACKLOG).
