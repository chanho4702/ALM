## 0. 제품 포지셔닝 (2026-08-28 사용자 확정)

**우리는 온프레미스 지라(Jira Server / Data Center)를 대체하고, Jira Cloud의 좋은 기능을 흡수해
더 나은 서비스를 만든다.** 지라 클론이 아니라는 기존 정체성 위에 "대체 가능성"이 얹힌다.
이 포지셔닝이 아래 판단을 바꾼다.

| 포지셔닝 귀결 | 요구사항에 미치는 영향 |
|---|---|
| **이관 없이는 대체가 아니다** | 온프렘 지라 데이터 가져오기(프로젝트·이슈·코멘트·첨부·이슈 키 보존)가 1급 요구사항. 기존 CSV 항목을 Could에서 Should로 올렸다(§8-17) |
| **아틀라시안이 해주던 운영을 우리가 한다** | 관리 콘솔(사용자·그룹·라이선스 수준의 접근 관리), 백업·복구, 감사 로그가 클라우드 대체보다 무게가 크다(§5.9) |
| **클라우드의 강점을 골라 흡수한다** | 온프렘 DC에 없거나 약한 것(자동화 룰, 타임라인, 캘린더, 신형 대시보드 가젯, 폼)이 차별점 후보다. 이번 릴리스 제외는 유지하되 로드맵에서 지우지 않는다 |
| **기존 지라 사용자의 자산을 존중한다** | 온프렘 팀은 JQL 저장 필터·대시보드 쿼리를 이미 갖고 있다. JQL 전면 도입은 여전히 하지 않되, **JQL 읽기 호환(가져오기 시 번역)**을 정책 결정 대상으로 올렸다(§10-6) |
| **ALM 특색이 상회 지점이다** | 한국어 스마트 검색·필터 URL 공유·단순 시간추적은 지라 대비 우위로 유지한다. 대체 요건이 특색을 지우지 않는다 |

온프렘 대체 시 유리한 점도 기록한다: 우리 플랫폼은 이미 자체 호스팅(Docker·nginx·게이트웨이),
Keycloak SSO, PostgreSQL, 구조화 로그·Grafana 관측을 갖췄다. 온프렘 지라가 요구하는 인프라
전제 대부분이 이미 서 있으므로, 갭은 애플리케이션 기능과 관리 도구에 집중된다.

## 1. 문제 정의

alm-front는 지라의 구조(전역 셸·보드/백로그·커스텀 워크플로 스킴)를 상당 부분 재현했고
백엔드도 프로젝트·이슈·스프린트까지 올라왔다. 그런데 **팀이 실제로 한 스프린트를 계획하고
끝내고 회고하는 흐름이 아직 닫히지 않는다.** 구체적으로:

- 스프린트에 **목표도 기간도 없다.** `name/state/startedAt/completedAt`만 있어 "무엇을 위한
  스프린트였나", "언제까지인가"가 제품 안에 남지 않는다.
- 계획 단계에서 **얼마나 담았는지 합계가 안 보인다.** 이슈별 예상 시간은 있는데 스프린트·백로그
  단위 합계가 없다.
- 스프린트를 완료하면 미완료 이슈가 **무조건 백로그로 떨어진다**(프론트·백엔드 동일). 지라는
  다음 스프린트로 넘길지 백로그로 보낼지 고르게 한다.
- 끝난 뒤 볼 게 없다. **번다운·스프린트 리포트가 전무**하다. 현재 리포트는 상태 카운트 타일과
  담당자 분포뿐이라 "이번 스프린트가 어땠는지"를 답하지 못한다.

즉 지라 대비 갭이 가장 넓고 제품 가치 손실이 큰 곳은 화면 개수가 아니라 **스크럼 사이클의
뒷부분(계획 정밀도 → 완료 처리 → 회고 근거)**이다. 지금 다루는 이유는, 이 부분이 백엔드
런타임 전환(§9)과 같은 데이터(상태 변경 이력·스프린트 메타)를 필요로 하기 때문이다. 나중에
붙이면 이력이 비어 있어 리포트가 과거를 재구성할 수 없다.

## 2. 대상 사용자

| 페르소나 | 하는 일 | 현재 막히는 지점 |
|---|---|---|
| 스크럼 마스터 / PM | 스프린트 계획·시작·완료, 회고 자료 준비 | 목표·기간 부재, 리포트 없음, 완료 시 이관 선택 불가 |
| 개발 담당자 | 보드에서 자기 작업 진행, 시간 기록 | 스프린트 남은 기간·잔여량을 알 수 없음 |
| 프로젝트 관리자 | 워크플로·이슈 타입 구성 | 전이 규칙·필수 필드 통제 수단 없음(R2) |
| 이해관계자(뷰어) | 진행 상황 확인 | 권한 개념이 없어 뷰어 전용 접근 불가(R2) |

## 3. 성공지표 (검증 가능한 완료 기준)

실사용 데이터가 없는 단계라 정량 지표 대신 **완주 가능성**으로 정의한다.

1. 한 프로젝트에서 화면만으로 다음이 끊김 없이 가능하다: 스프린트 생성 → 목표·기간 입력 →
   백로그에서 담기(합계 확인) → 시작 → 진행 → 완료(미완료 이슈 이관 대상 선택) → 스프린트
   리포트·번다운 확인.
2. 번다운·스프린트 리포트의 수치가 **서버가 보존한 상태 변경 이력으로 재현**된다. 브라우저를
   바꾸거나 다른 사용자가 열어도 같은 값이 나온다.
3. 스코프 변경(스프린트 시작 후 추가·제거된 이슈)이 리포트에 별도로 구분되어 보인다.
4. 기존 258 케이스가 깨지지 않고, 새 기능마다 스토어 단위 + 통합 테스트가 추가된다.

## 4. 범위

### 포함 (이번 분석·기획 대상)

Jira Software 코어 8영역의 갭 인벤토리(§5) 전체와, 그중 R1~R3로 편성된 항목(§6~§8).

### 명시적 제외 (이번 릴리스에서 만들지 않는다)

- **Jira Service Management** — 요청 포털·SLA·큐·고객 개념
- **Jira Work Management / Jira Product Discovery** — 비개발 부서 뷰, 아이디어 랭킹
- **Automation 룰 엔진** — 트리거/조건/액션/스마트 값. 이번 릴리스 제외이지만 **로드맵에 남긴다**
  (온프렘 DC에 약한 영역이라 클라우드 흡수 차별점 후보, §0)
- **개발 도구 연동** — 스마트 커밋, 브랜치·PR·배포 패널, Code/Deployments 뷰
- **Plans(어드밴스드 로드맵)** — 다중 프로젝트 시나리오 계획·용량 플래닝
- **마켓플레이스 앱·REST 공개 API·웹훅**, **AI 기능(Rovo)**, **모바일 앱**
- **JQL 문법의 1급 도입** — 검색 입력 문법은 한국어 스마트 검색을 유지한다. 단 온프렘 이관
  자산을 위한 **JQL 읽기 호환**은 제외가 아니라 정책 결정 대상이다(§10-6)
- **데이터 레지던시·SAML/SSO 재설계** — 인증은 플랫폼 Keycloak 확정 구성을 그대로 쓴다
- **화면(Screen)/필드 구성 스킴 전면 도입** — 커스텀 필드는 R3에서 최소 형태만 검토

### 5.6 리포트

지라 코어 리포트는 스크럼 6종(번다운·번업·스프린트 리포트·벨로시티·에픽 번다운·릴리스
번다운/버전 리포트), 칸반 2종(컨트롤 차트·누적 흐름도), 이슈 분석 11종(평균 연령·생성 대
해결·파이·최근 생성·해결 시간·단일 그룹·필드 변경 이후 경과·시간 추적·사용자 작업량·버전
작업량·작업량 파이)이다.

### 5.9 온프렘 대체 요건 (지라 코어 기능표 밖, §0에서 파생)

클라우드 지라를 쓰던 팀에겐 아틀라시안이 대신 해주던 일이, 온프렘 대체 제품에서는 우리 기능이
된다. 지라 기능 인벤토리에는 안 잡히지만 "대체 가능"의 조건이라 별도로 세운다.

| 대체 요건 | 우리 현재 | 판정 | 처리 |
|---|---|---|---|
| 기존 지라 데이터 가져오기(프로젝트·이슈·코멘트·이슈 키 보존) | 없음 | ❌ | **S** — 이관 없이는 대체 불가 |
| 첨부파일 이관 | 없음(첨부 기능은 있음) | ❌ | S — 이관 도구와 함께 |
| 사용자·그룹 매핑(지라 계정 → Keycloak 사용자) | 없음(목업 4명) | ❌ | S — 사용자 디렉터리와 한 묶음 |
| JQL 저장 필터 자산 이관 | 없음 | ❌ | ❓ 정책대기(§10-6) |
| 관리 콘솔(사용자·그룹·접근 관리 화면) | 없음(전역 설정은 스킴만) | ❌ | S |
| 백업·복구 절차 | 플랫폼 차원 미정 | ❌ | S — 운영(`platform-ops`) 협의 필요 |
| 감사 로그(누가 무엇을 언제) | 없음(BACKLOG #6) | ❌ | S — 온프렘에서는 규정 대응 요소 |

| 시스템 상태·용량 가시성 | Grafana 관측은 있음(앱 지표는 없음) | 🟡 | C |

온프렘 지라가 요구하던 인프라(자체 호스팅·SSO·DB·리버스 프록시)는 우리 플랫폼에 이미 있다.
따라서 이 표의 무게중심은 인프라가 아니라 **이관 도구와 관리 화면**이다.

## 6. 릴리스 슬라이싱 (수평)

세로로 한 기능을 깊게 파지 않고, **매 릴리스가 사용자 흐름을 끝까지 완주시키는** 얇은 층으로
자른다.

- **R1 — 스크럼 한 사이클을 끝까지 돌린다** (Must) — ✅ 전부 완료(2026-08-29)
  요약 대시보드는 R1과 별개로 2026-08-28 구현했다(설계: `../superpowers/specs/2026-08-28-project-summary-dashboard-design.md`)
  스프린트 메타(목표·기간) → 계획 합계 → 완료 시 이관 선택 → 상태 이력 서버 보존 →
  번다운 + 스프린트 리포트. 이 5개가 붙으면 §3-1 완주 기준이 처음으로 참이 된다.
- **R2 — 여러 사람이 같은 프로젝트를 운영한다** (Should)
  사용자 디렉터리·권한/역할, 워크플로 전이 규칙, 해결(Resolution), 버전/릴리스, 첨부파일,
  워처·알림 서버화, 대량 변경, 서버 검색·페이징, 리포트 확장(번업·벨로시티·CFD·컨트롤 차트),
  **온프렘 지라 이관 도구와 관리 콘솔(§5.9)**.
- **R3 — 지라 세부 편의를 메운다** (Could)
  리치 텍스트·멘션, 커스텀 필드(단순 타입), 컴포넌트, 캘린더·목록 인라인 편집, 카드 레이아웃·
  쿼리 퀵필터/스윔레인, 대시보드 가젯, 이슈 이동·복제, 투표·플래그, 휴지통·감사 로그,
  CSV, 실시간 협업.

## 7. 유저스토리 + 수용조건 (R1)

### S1. 스프린트 목표와 기간을 정한다 — ✅ 완료 (2026-08-28)

구현: 백엔드 `V4__sprint_planning.sql` + `GET`·`PUT /api/alm/sprints/{id}`,
프론트 `updateSprint`·`SprintEditModal`·백로그 패널 머리글 표기.

스크럼 마스터로서, 스프린트에 목표와 시작·종료 예정일을 남겨 팀이 무엇을 언제까지 하는지
합의하고 싶다.

```
Given 계획 상태(planned)인 스프린트가 있다
When 스프린트 편집에서 목표와 시작·종료 예정일을 입력해 저장한다
Then 백로그의 스프린트 패널 머리글에 목표와 기간이 표시된다

Given 시작 예정일이 종료 예정일보다 늦게 입력됐다
When 저장을 시도한다
Then 저장이 거부되고 사유가 표시되며 입력값은 그대로 남는다
```

### S2. 스프린트에 담은 작업량 합계를 본다 — ✅ 완료 (2026-08-28)

구현: `labels.estimateSummary` + `PanelEstimateSummary`(스프린트·백로그 머리글 공용).
단위는 §10-1의 (a) 예상 시간(h) 가정을 따랐다.

PM으로서, 계획 중 스프린트에 담긴 작업량 합계를 보고 과부하 여부를 판단하고 싶다.

```
Given 스프린트에 예상 시간이 입력된 이슈와 미입력 이슈가 섞여 있다
When 백로그 화면을 연다
Then 스프린트 머리글에 이슈 수와 예상 시간 합계가 표시되고, 미입력 이슈 수가 함께 드러난다

Given 백로그에서 이슈를 스프린트로 드래그했다
When 이동이 끝난다
Then 합계가 즉시 갱신된다
```

### S3. 스프린트를 완료할 때 미완료 이슈의 행선지를 고른다 — ✅ 완료 (2026-08-28)

구현: 완료 API에 `moveUnfinishedToSprintId`(같은 프로젝트·미완료 스프린트만) 추가,
프론트 `completeSprint(id, { moveUnfinishedTo })` + `SprintCompleteModal`(미완료 목록 + 행선지 라디오).

스크럼 마스터로서, 완료되지 않은 이슈를 다음 스프린트로 넘길지 백로그로 보낼지 고르고 싶다.

```
Given 진행 중 스프린트에 완료되지 않은 이슈가 3건 있다
When 완료를 실행한다
Then 미완료 3건의 목록과 행선지 선택(다음 계획 스프린트 / 백로그)이 먼저 제시된다

Given 행선지로 다음 계획 스프린트를 선택했다
When 완료를 확정한다
Then 미완료 이슈는 그 스프린트로 이동하고 완료 이슈는 스프린트에 남는다
```

### S4. 스프린트 진행이 번다운으로 보인다 — ✅ 완료 (2026-08-29)

구현: `reportMetrics.burndownSeries`(이력 재생) + `ReportsPage`(Recharts, 기준선 점선/잔여선 계단).

담당자로서, 남은 작업과 남은 기간을 한 그림으로 보고 싶다.

```
Given 시작·종료 예정일이 있는 진행 중 스프린트가 있다
When 리포트에서 번다운을 연다
Then 기간을 가로축으로, 잔여 작업량을 세로축으로 하는 실제선과 기준선이 그려진다

Given 스프린트 기간 중 이슈가 완료 상태로 바뀐 이력이 있다
When 번다운을 다시 연다
Then 그 시점에 잔여 작업량이 내려간 계단이 나타난다
```

### S5. 끝난 스프린트를 리포트로 회고한다 — ✅ 완료 (2026-08-29)

구현: `reportMetrics.sprintReport` — 완료/미완료(이관 행선지)/스코프 변경 3묶음.

스크럼 마스터로서, 무엇이 끝났고 무엇이 남았으며 도중에 무엇이 추가됐는지 보고 싶다.

```
Given 완료된 스프린트가 있다
When 스프린트 리포트를 연다
Then 완료 이슈 / 미완료 이슈(이관 행선지 포함) / 시작 후 추가·제거된 이슈가 구분되어 나열된다

Given 스프린트 시작 후 이슈 1건이 추가됐다
When 리포트를 연다
Then 그 이슈가 스코프 변경으로 표시된다
```

### S6. 리포트 수치가 누구에게나 같다 — 🟡 서버 이력 기록 완료 (2026-08-29)

구현: `V5__issue_change_log.sql`(field/from_value/to_value 일반 구조, STATUS·SPRINT만 기록) +
생성·수정·보드 이동·랭크 이동·스프린트 완료 이관 전 경로에서 기록 +
`GET /api/alm/projects/{id}/changes`(field·sprintId·since 필터, 시간 오름차순).
스프린트 필터는 전이의 양쪽을 잡는다 — 떠난 줄까지 봐야 원래 스프린트의 "빠진 이슈"를 셀 수 있다.
남은 것: 이 이력을 번다운 시리즈로 집계하는 API와 화면(S4·S5에서 소비).

PM으로서, 내 브라우저가 아니라 서버가 보존한 이력으로 리포트가 계산되기를 원한다.

```
Given 이슈 상태가 여러 번 바뀐 스프린트가 있다
When 다른 사용자가 같은 스프린트의 번다운을 연다
Then 동일한 계단과 합계가 표시된다

Given 브라우저 저장소를 비운 뒤 다시 접속했다
When 스프린트 리포트를 연다
Then 리포트 내용이 이전과 동일하다
```

## 10. 열린 정책 결정

- **❓정책대기 1 — 추정 단위.** 지라 스크럼 리포트(번다운·벨로시티)는 스토리 포인트를 기본
  단위로 쓴다. 우리 확정 결정은 "예상 시간 + 기록 2값 단순화"다. 선택지: (a) 번다운을 예상
  시간(h) 기준으로 그린다 — 확정 결정 유지, 추가 필드 없음 (b) 이슈 수 기준으로 그린다 —
  가장 단순, 정밀도 낮음 (c) 스토리 포인트 필드를 추가하고 보드 설정에서 단위를 고른다 —
  지라 동등성 최고, 확정 결정과 충돌 소지. **R1 착수 전에 사용자 확인 필요.** 이 문서의
  S2·S4는 (a)를 가정해 작성했다.
- **✅결정 2 — 차트 렌더링 수단 (2026-08-28 사용자 확정).** 오픈소스 라이브러리를 써도 되며
  **라이선스는 MIT만** 허용한다. 후보: Recharts(MIT), Chart.js(MIT), visx(MIT), Nivo(MIT).
  ⚠️ Apache ECharts는 **Apache-2.0**이라 MIT 조건에 맞지 않는다 — 쓰려면 조건을 다시 정해야 한다.
  좌표축 차트(번다운·벨로시티·CFD)를 만들 때 도입하고, 그때 `@chanho` 토큰으로 색·타이포를
  덮어 디자인 언어를 맞춘다. **요약 대시보드(2026-08-28 구현)는 라이브러리 없이** 토큰 마크업으로
  끝냈다 — 색 분리 검증 결과가 범주형 팔레트를 기각했기 때문이다(설계 문서 §4).
- **⚠️확인필요 3 — 스프린트 기간과 실제 시작·완료 시각의 관계.** 예정일을 넘겨 완료할 때
  번다운 가로축을 예정 종료일까지로 고정할지, 실제 완료일까지 늘릴지.
- **✅결정 4 — 이력 보존 범위 (2026-08-29).** 지금은 상태와 스프린트 소속 둘만 남긴다.
  테이블은 `field`/`from_value`/`to_value` 일반 구조라 필드를 추가해도 컬럼은 그대로이고
  CHECK 제약에 값을 더하는 마이그레이션 한 줄만 필요하다(제약은 지우지 않는다 — 코드 오타가
  조용히 저장되는 것을 DB가 막는다). 모든 필드 변경을 남기는 감사 로그는 별개 과제(§5.9)로 둔다 — 리포트에 필요하지
  않은 데이터로 이력 테이블을 불리지 않는다.
- **❓정책대기 5 — 리포트 화면 위치.** 지라는 프로젝트 좌측 메뉴에 리포트 섹션을 둔다. 우리는
  기존 `/projects/:id/dashboard`를 리포트 허브로 승격할지, 별도 경로를 낼지 미정.

- **❓정책대기 6 — JQL 자산 호환 범위.** 온프렘 지라를 쓰던 팀은 JQL로 만든 저장 필터와
  대시보드 쿼리를 갖고 있다. 선택지: (a) 이관 시 JQL을 한국어 스마트 쿼리로 번역해 가져온다
  (번역 불가 구문은 원문 보존 후 경고) (b) JQL 문자열을 읽기 전용으로 저장만 하고 실행은
  하지 않는다 (c) 이관 대상에서 제외한다. 검색 입력 문법을 스마트 검색으로 유지한다는 확정
  결정은 어느 선택지에서도 바뀌지 않는다.

## 10-1. 사용자 방향 지시 (2026-08-28, MVP 이후 고려 대상)

MVP 범위 밖이지만 설계를 이 방향에 맞춰 둔다. 지금 구현하지 않는다.

| 지시 | 반영 계획 |
|---|---|
| **워크플로를 React Flow로 그려서 설정** | 전이(Transition) 편집을 노드-엣지 캔버스로 만든다. `@xyflow/react`는 MIT라 위 라이선스 조건을 만족한다. 상태 모델(`WorkflowStatus`)은 이미 있으니 엣지(전이)와 규칙(조건·검증기)이 추가 데이터다 — §5.7 "전이 정의" 항목(Should)과 같은 작업이다 |
| **모든 설정을 기본값과 프로젝트별로** | 이미 스킴(전역 기본) ↔ 프로젝트 커스텀 구조가 있다(`resolveSettings`). 새 설정(전이 규칙·필드·우선순위 등)을 추가할 때마다 **같은 2단 구조에 얹는다** — 설정마다 다른 저장 위치를 만들지 않는다 |
| **필요하면 화면을 새로 만들고 오픈소스 사용 가능** | 전역 `/settings`와 프로젝트 `설정` 탭 두 곳이 같은 편집기를 공유한다(StatusEditor가 이미 쓰는 패턴). 라이브러리는 MIT만 |

## 11. 핸드오프

다음 단계는 R1 상세 설계다. 소비자별로 필요한 것:

- **디자이너(`product-design`)**: 지라 레퍼런스 캡처가 아직 없다. 대상 화면은 백로그 스프린트
  머리글(목표·기간·합계), 스프린트 완료 모달(이관 선택), 번다운·스프린트 리포트. 임의 창작 대신
  지라 공식 문서 화면(§참고 소스의 번다운·리포트 문서)을 근거로 삼고, 캡처를 확보하면 이 문서에
  경로를 추가한다.
- **백엔드(`platform-backend` 규약)**: 계약 확정 대기 항목 — 스프린트 메타 필드 3종, 완료 API의
  이관 대상 파라미터 형태, 이력 테이블 스키마와 리포트 집계 응답 shape, 이력 이벤트를 Redis
  Streams로 발행할지 여부.
- **프론트(`platform-frontend`)**: `jiraStore.ts`가 유일한 교체 지점이라는 규칙을 유지한다.
  R1 기능은 목업(localStorage)과 REST 어댑터 양쪽에 같은 시그니처로 들어가야 한다.
- **리뷰(`code-review`)**: §3 완료 기준 4개가 판정 기준이다.
